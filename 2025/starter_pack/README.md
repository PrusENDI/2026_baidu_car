# 百度组入门手册

## 百度组与其他组别的不同
这或许是新来百度组的队员们最好奇也最关心的问题了。百度创意组在很多方面都与传统组别（甚至其他创意组）有许多的不同点；关于技术上的内容在之后会详细写到，在这里我想简单说一下百度创意组给我的感受。首先，这个组别的氛围（尤其是比起卷生卷死的传统组别来说）是非常好的，由于百度组赛制与规则的特殊性，该组别的各个队伍之间相互帮助、一起解决问题的行为并不会为更强的队伍带来劣势，因此组别内存在大量的相互帮助，而非技术强的队伍藏着掖着，技术弱的队伍死活找不到头绪。就我个人来说，我更喜欢这样的竞赛氛围，我也认为这才是智能车这种类型比赛该有的比赛环境。

其次是上文提到的赛制与规则的特殊性。就前几届的经验来看，百度创意组最重要的是实现功能而非卷时间等（当然，在规定时间内完赛是硬要求），因此可以更加专注于稳定实现小车的功能而非花大量时间在一些无意义的细节上，这个在上手之后或许会有更多的感觉。

## 小车的硬件
硬件一般由合作的公司提供，其中也包括下位机（或许也会包含下位机），一般是金属积木，可以很方便的拼装起来，留在实验室的去年小车是我们匆忙拼装起来的，因此很乱，你们可以按照拼装手册重新整理一下。

## 百度创意组所需的技术栈

### 编程语言
最重要的就是Python（脚本语言写起来真的很舒服），就近几年来看，百度创意组更加注重在PaddlePaddle框架下的各种机器学习功能（包括OCR、巡航、目标识别、大语言模型等，或许今年会加入更多内容也说不定）。要是想看明白其中的机器学习部分直接去学习一点PyTorch即可，没有必要专门学习飞桨框架（因为这东西用得实在太少了XD）。其次就是C与CPP，当然相信你们既然打了这么长时间传统组别这个不用特别强调了。

### 硬件知识
百度组应该会有一个大体的方案，其中解决了一大部分运动学上的问题，因此可以不用过于注重于此方面。对于复杂的控制，大家应该也有很好的下位机可以用（至于上位机更是豪华，是为数不多全员Jetson的），最大的问题是官方给出的运动学方案有大量奇怪的代码耦合，建议到手之后研究给一部分过于复杂的功能先写一份代码解耦的、更简洁的函数，然后在此基础上再去进行后续开发，否则等代码进一步膨胀之后调整起来会非常困难。

### 往届代码
最具有参考性的应该就是上一届代码。我们的代码存放在小车的Jetson中，位置在*code_vehicle_wbt*中，在前期的准备时间中你们可以尽可能地去研究上一年的车，把各个功能都看看，也熟悉一下百度组的代码项目。Jetson的信息写在文档末尾了。

## 踩过的坑
在这个组里还是会有不少的坑的，尤其是以下几点：
* 硬件并不完美。我们这一届就遇到了机械臂高度不够、官方设计的线路在实际使用中会磕磕绊绊等问题。得益于小车一直都依赖金属积木，这一点其实很好解决。但是一定要在发现之后立刻想办法解决此方面问题，同时也不要被单个小问题卡住。最好的方案是，由主导项目的人发现问题后先发给队员让队员来思考一下这些边缘问题的解决方案，然后暂时忽视这个小问题先尝试跑通之后的流程。等解决方案来了之后，再马上回头解决这个小问题。
* 官方代码实际上是硬编码，并没有应变能力。我个人觉得这个很明显是用来筛选那些试图拿baseline方案直接上场的人的，所以一定要先找出这部分代码重写逻辑。

## 应当准备的...
* 首先，你应当有一台Ubuntu物理机，这在开发Jetson时至关重要。为什么？因为老黄只在这里准备了大量的开发工具...而虚拟机总是会出现大量很耗时间的问题，尤其是在刷写系统等的时候。
* 支持X11的终端。首先远程调试摄像头必备这个东西，直接输入CHEESE比插屏幕或者进NoMachine都要方便得多。另：当遇到官方的代码总是卡死而不报错时，建议使用支持X11的客户端重新运行...这部分原因我倒是懒得排查了，你们有兴趣可以看看，尤其是推理后端的首次运行必须使用支持X11的客户端。
* NoMachine。这个远程桌面软件真的很好用，当然，我个人更加建议将一切都放在终端中进行。然而如果你需要低延迟的查看某些生成在小车里的图表，用这个能节省你很多时间。

## 线上赛
线上赛一般是线下赛的前置任务，所以一定要考虑到后续对小车的兼容性。线上赛应该是在飞桨开发者平台完成一项诸如图像识别等的任务（基本是一键训练所以没什么好说的），但是队伍里一定要有几个负责任的数据标注！
