# 按键启动监督器设计

## 目标

为 Orin 上的比赛程序提供统一的开机启动入口。系统开机后立即启动并预热推理后端，但不初始化车辆、不复位机械臂，也不执行比赛任务。只有端口 5 的四键模块长按第 4 键并产生 MC602 键值 `12` 后，才启动现有 `car_start_2026.py`，由它执行 `init()` 和完整任务流程。

主程序正常结束或异常退出后，启动入口必须返回按键等待阶段，以便再次启动。推理后端在等待阶段和任务运行阶段都应受到监控；后端退出后应自动重新拉起。

## 非目标

- 不改动现有完整任务的执行顺序。
- 不把车辆 `init()` 提前到按键触发之前。
- 不在按键监听进程中创建 `MyCar`。
- 不改动 MC602 底层按键映射或消抖算法。
- 不为正在运行的任务实现推理客户端透明重连；后端在任务期间崩溃时由监督器重启，当前主程序可按现有行为失败或退出，下一轮启动前必须重新确认后端就绪。

## 总体架构

实现由三个组件组成：

1. `scripts/start_with_key.sh`：常驻监督器，管理后端、按键等待和主程序生命周期。
2. `scripts/wait_for_start_key.py`：一次性按键监听器，只负责显示等待状态并等待端口 5 的键值 `12`。
3. `systemd/baidu-smart-key-start.service`：Orin 开机启动单元，负责启动监督器并在监督器异常退出时重启。

监督器的主循环如下：

```text
启动并监控推理后端
        ↓
等待后端三个服务全部就绪
        ↓
运行按键监听器，等待端口 5 长按第 4 键
        ↓
再次确认后端仍然就绪
        ↓
前台运行 car_start_2026.py（包含 init 和完整任务）
        ↓
主程序退出，记录退出码
        └────────────────────→ 回到后端检查与按键等待
```

## Shell 监督器

`scripts/start_with_key.sh` 使用项目目录作为工作目录，并通过脚本自身位置解析项目根目录，避免依赖调用者当前目录。

职责如下：

- 使用锁文件防止 systemd 实例和人工启动实例同时运行。
- 检查 `infer_back_end.py` 进程是否存在；不存在时以 `python3` 启动。
- 在后台运行后端看护循环，定期检测后端进程并在退出后重新拉起。
- 在允许按键启动前确认配置中的三个推理服务端口 `5001`、`5002`、`5005` 均返回就绪状态。
- 后端就绪后运行 `wait_for_start_key.py`。
- 按键监听器成功退出后再次检查后端就绪状态，防止等待按键期间后端刚好重启。
- 前台运行 `car_start_2026.py`，保留其标准输出、标准错误和退出码。
- 主程序退出后等待一个短暂的冷却时间，再进入下一轮。
- 收到 `SIGTERM` 或 `SIGINT` 时终止当前主程序和后端看护进程，然后退出，由 systemd 完成服务生命周期管理。

后端重复检测沿用当前项目按脚本路径识别 `infer_back_end.py` 的行为。监督器不会在已检测到后端进程时重复启动它。

## 后端就绪检查

仅检测进程存在不足以证明模型已完成加载和预热。就绪检查必须使用后端现有的 ZMQ 健康协议：向服务发送 `ATATA`，只有收到 JSON `true` 才视为就绪。

检查覆盖配置中的三个服务：

- `lane`：端口 `5001`
- `task`：端口 `5002`
- `goods`：端口 `5005`

每次探测必须设置发送和接收超时，探测失败后关闭带有 `LINGER=0` 的 socket 并重试，避免后端启动失败时无限阻塞在单次 `recv()`。等待过程应持续进行，同时由看护循环负责重启已退出的后端。

就绪探测可由监督器调用轻量 Python 代码完成，但不得构造 `MyCar` 或加载车辆任务模块。

## 按键监听器

`scripts/wait_for_start_key.py` 的行为如下：

1. 创建 `ScreenShow`。
2. 创建 `Key4Btn(5)`。
3. 显示 `wait to start`。
4. 以约 `0.1` 秒周期调用 `get_key()`。
5. 忽略除整数 `12` 以外的所有返回值。
6. 收到 `12` 后显示 `started!!!`，短暂停留后以退出码 `0` 结束。

MC602 驱动中，键值 `12` 表示第 4 键持续长按事件。监听器收到第一次 `12` 后立即退出，因此一次长按只能启动一次主程序。

按键监听器和主程序位于两个先后运行的 Python 进程中。监听器退出后，主程序才创建 `MyCar` 及端口 1 的 `Key4Btn`，避免端口 5 与端口 1 的按键实例在同一进程中共享 MC602 驱动状态。

监听器收到 `KeyboardInterrupt` 或终止信号时应以非零状态退出。监督器不得把非零退出当作有效启动事件；若服务仍在运行，则重新进入后端检查和按键等待。

## 主程序生命周期

按键触发后，监督器直接运行现有 `car_start_2026.py`。该文件继续负责：

- 调用 `init()`；
- 创建 `MyCar`；
- 复位机械臂和底盘；
- 连接已预热的推理后端；
- 按原顺序执行完整任务。

现有 `ClintInterface` 自动启动后端的能力保留不变，作为非监督器入口和竞争条件下的兼容保障。

监督器记录主程序退出码，但无论退出码是否为零，都返回按键等待阶段。为避免崩溃后快速循环，应在重新等待前加入短暂延迟。

## systemd 服务

`systemd/baidu-smart-key-start.service` 使用以下运行约束：

- `User=jetson`
- `WorkingDirectory=/home/jetson/workspaces/baidu_smart_2026_7_17`
- `ExecStart` 指向项目内 `scripts/start_with_key.sh`
- `Restart=always`
- 设置短暂的 `RestartSec`
- 标准输出和错误输出进入 systemd journal
- 服务停止时终止整个控制组，避免遗留主程序或后端子进程

服务安装需要把单元文件链接或复制到 `/etc/systemd/system/`，执行 `systemctl daemon-reload`，然后执行 `systemctl enable --now baidu-smart-key-start.service`。安装属于 Orin 系统变更，实施时应在同步代码并验证脚本后单独执行。

## 错误处理与可观测性

- 后端启动失败：记录错误并持续重试，不进入按键可启动状态。
- 后端启动缓慢：持续显示加载状态并等待，不设置无限阻塞的单次 ZMQ 调用。
- 按键设备初始化失败：监听器非零退出，监督器延迟后重试。
- 主程序异常退出：记录退出码，恢复后端后重新等待按键。
- 重复启动监督器：锁获取失败的实例立即退出并记录原因。
- 服务日志：统一由 journal 收集；后端和主程序输出不静默丢弃。

屏幕状态至少包括：

- `loading inference`：后端尚未全部就绪。
- `wait to start`：后端已就绪，可以长按启动。
- `started!!!`：已接受启动事件，即将运行主程序。

## 验证策略

不连接车辆硬件时执行：

- `bash -n scripts/start_with_key.sh` 验证 Shell 语法。
- Python 编译检查按键监听器及后端探测辅助代码。
- 使用模拟 `Key4Btn` 验证非 `12` 键值不会启动，首次 `12` 只产生一次成功退出。
- 使用模拟进程和健康探测验证后端不存在时启动、已存在时复用、退出时重启。
- 验证主程序退出码为零和非零时监督器都会返回等待循环。
- 使用 `systemd-analyze verify` 检查服务单元语法（环境提供该命令时）。

在 Orin 上执行：

- 冷启动验证后端自动拉起并完成三个端口的健康检查。
- 验证后端就绪前按键不会启动 `MyCar`。
- 验证端口 5 长按第 4 键后才出现车辆初始化动作。
- 验证主程序退出后屏幕重新显示 `wait to start`。
- 人工终止后端，验证看护循环会重新启动并恢复到可启动状态。
- 验证 systemd 开机启动、停止和重启不会遗留重复进程。

## 验收标准

- Orin 开机后无需登录即可启动监督器和推理后端。
- 推理后端在等待按键期间完成模型加载和预热。
- 按键触发前不会调用 `init()`，车辆和机械臂不产生初始化动作。
- 只有端口 5 的键值 `12` 能启动完整任务流程。
- 每次按键最多启动一个主程序实例。
- 主程序结束或失败后能够重新等待按键。
- 后端退出后能够自动重启，且下一次任务只在后端重新就绪后启动。
