# MC602 掉线恢复设计

## 目标

上位机启动时若 MC602 下位机尚未上电，应持续等待而不是卡死或启动完整任务。任务运行期间若 MC602 掉线，应尽快停止当前任务和车辆输出，释放硬件资源，并由按键启动监督器在下位机恢复后重新进入按键等待阶段。恢复后不得自动继续中断的任务。

## 范围

- 为 MC602 串口通信提供统一、明确的掉线信号。
- 在完整任务入口集中处理掉线，执行安全停止和资源清理。
- 让启动监督器等待 MC602 可用，并在任务因掉线退出后重新等待设备和启动按键。
- 保留现有推理后端看护、按键启动和 journal 日志行为。

不实现任务断点续跑，不为推理后端增加透明重连，也不改变业务任务顺序。

## 架构

### 通信层

`SerialWrap` 负责统计连续的 MC602 请求失败。单次超时仍允许作为瞬时故障处理；连续失败达到小阈值后，通信层抛出专用 `ControllerDisconnected` 异常。一次成功应答会清零失败计数。

异常必须从统一的串口事务入口产生，使底盘、机械臂、按键和传感器访问遵循同一规则。串口事务仍使用现有进程内锁，避免同一进程中多个线程交错收发。

### 主程序

`car_start_2026.py` 在完整任务最外层捕获 `ControllerDisconnected`。捕获后记录明确日志，设置停止状态，尝试停止底盘和机械臂输出，并释放 `MyCar` 已创建的线程、摄像头及其他资源。清理过程必须容忍 MC602 已不可通信，不能因二次串口异常阻止进程退出。

主程序以专用非零退出码结束，使监督器能够区分正常结束、一般异常和下位机掉线。

### 启动监督器

监督器在创建按键监听器之前先运行一次独立的 MC602 就绪探测。探测进程必须有超时：设备未上电、串口未枚举或控制器无响应时均返回“未就绪”，监督器记录状态并延迟重试，不启动主程序。

按键监听器收到启动事件并退出、释放串口后，监督器再次确认推理后端和 MC602 就绪，再启动完整任务。任务因下位机掉线退出后，监督器回到 MC602 就绪探测；设备恢复后重新显示等待启动，不自动开始任务。

## 状态流转

```text
等待 MC602
  -> MC602 就绪
  -> 等待启动按键
  -> 收到启动事件并释放监听串口
  -> 再次确认后端和 MC602
  -> 运行完整任务
  -> 正常/异常结束：短暂延迟后等待 MC602
  -> MC602 掉线：安全清理后立即等待 MC602
```

## 故障与安全处理

- MC602 启动时未上电：持续重试，不创建主任务。
- 瞬时单次通信失败：不立即终止任务，避免把偶发超时当成掉线。
- 连续通信失败：抛出掉线异常并终止任务。
- 掉线后的停止指令也失败：记录错误但继续清理和退出，因为无法向已断开的控制器保证送达停止指令。
- MC602 恢复：必须重新按启动键，不恢复旧任务。
- 服务收到 `SIGTERM`：沿用现有控制组清理逻辑，终止主程序和后台看护。

## 验证

只保留最小关键验证：

1. 通信连续失败达到阈值时产生掉线异常，成功应答会重置计数。
2. MC602 就绪探测失败时监督器不启动按键监听或主程序。
3. 主程序因掉线退出后，监督器返回设备等待阶段；设备恢复后仍需按键才能启动。
4. 对相关 Python 和 Bash 文件执行语法检查。
